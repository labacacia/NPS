# 普通 HTTPS 与 NPS reference 运行时：测量范围

状态：ca55bf2 默认 GC 实验答案正确，但未通过 512MiB RSS 门槛；
须完成明确资源配置下的重测才能宣称合格。
D20-01 依据[冻结方法](../../spec/conformance/alpha20/data_workflow_methodology.json)及
[精确运行时 oracle](result-oracle-observation-2026-11-02.cn.md)。本文补充测量边界，
不修改冻结要求。

## 对照路径与证据

两条路径共享相同种子不可变来源、稳定排序、结果存储及精确 COUNT/Int64 SUM。
C 提供普通 HTTPS JSON 的 create/aggregate/read/release 工具；D 使用受支持 NPS
客户端、明确版本化发现、公开 mTLS 网关、新 NIP 投影及独立认证接收端。
两者均检查当前 CA/来源策略。普通工具也在模型外处理数据，此 harness 不调用模型。

每次工作流独立捕获全部订单及退款订单，取得两组聚合，读取有界明细并释放两个结果，
答案必须精确符合 oracle。测量前另备一个共享来源引用及有界首个页面；每次完整来源
捕获必须具有相同快照哈希。两条路径引用共同不可变来源和相同五条真实记录，确保模型
文本逐字节相等。共享溯源准备/最终清理单列，临时结果自身的 create/release 均计入。
最后释放溯源引用，因此导出证据是历史捕获，不代表仍在线的后续查询会话。

## 重复、压缩、连接与字节

Release 模式运行 100/1000/100000 行。每条路径/连接/压缩组合先预热 3 次再测量
30 次，共 24 组观察、720 次正式工作流和 72 次预热。随连接状态交替首跑路径。
identity 与 gzip 响应分开记录，两者请求都不压缩；服务端实际观察 gzip 响应计数。

cold 指每次工作流新建前端连接，warm 指复用；禁用 TLS 会话恢复。不声称清空 CPU/
来源/模型缓存。D 当前每次操作新建下游客户端，该部署选择、重复发现和额外认证均计入，
不能泛化成 NCP 固有收益或成本。

TLS 下层计数流测量双向 TCP 字节流，包括 TLS record、HTTP/1.1 头、chunk 和载荷。
D 汇总公开及网关出站，C 测量直连；不保存内容、凭据、投影或密钥。
cold 前端关闭计入，下游连接在公开回复前关闭；warm 建连计入预热，最终关闭单列。
两者都不计 TCP/IP 包头和重传开销。这不是以太网抓包，也不只是载荷字节估算。

保留每组 30 个时延/字节值，报告 median 和 nearest-rank p95。RSS 与 OS 峰值覆盖整个
同进程测试宿主，检查 512MiB 上限，不能归因成某协议的内存节省。失败观察保留，不计
为合格。此单次 HTTP 实验不证明原生 NCP、Arrow/Flight/Protobuf、schema 变化/更新、
故障切换或通用公开 PKI 的效率。剩余 D20-01/04/08 义务及历史门槛继续保留。


完整分布、实际压缩、相同模型文本及内存状态，分别导出 identity/gzip 文件供已有

伪造计数、引用变更、虚构 usage 及虚报内存通过。正确性测试不等于 30 次正式实验。

## 默认 GC 失败与明确资源配置下的重测

ca55bf2 完成全部 720 次正式工作流，答案正确且 C/D 模型文本相等，但两条 100000 行
路径均超出原 RSS 上限；同进程峰值最高 1462.07MiB。所有负面观察保留，不能重标成
成功；仅凭 RSS 也不能断言存在持久对象泄漏。

审阅发现聚合循环对每行分组标量反复克隆 JSON document。来源 document 在最终分组
独立序列化前始终存活，因此可移除克隆而不改变结果。这是针对 D20-01 实际分配失败
所需的最小 D20-02 支持性修正，同时新增 managed heap/线程采样。

8daac11 的 256MiB 堆尝试完成了较小规模，但 100000 行结果创建被拒绝；当时没有记录
规范错误码，不能将其定性为 OOM。该失败尝试保留，并补充失败采样。

下一轮对两条路径明确设置四 CPU 的 OS affinity 与 384MiB managed heap 上限，仍检查
原 512MiB 进程 RSS 上限。此前 CLR 已报告四处理器，不能据此声称减少了处理器数量。
launch receipt 记录具体 CPU ID 和限制。这同时包含代码及部署配置变化，不能单独
归因其中一项的效果；测量期间不插入强制 GC。原默认 GC 失败继续保留。

两条路径同样预加载/缓存不可变 fixture 来源，每次实际 store 捕获仍复制数据。
这移除了测量来源的重复生成开销，改变的是已声明的来源准备方式，不改变一致性或协议。
宿主明确允许仅该冻结合成来源外发给模型，两条路径均执行 store 的 ToModel 检查；
缺少该出站来源证明的捕获不能进入真实模型调用。实验中断时保留逐组进度，以及有限的
错误码、堆和线程观察。

83fc03b 的来源缓存/384MiB 堆实验完成了全部正确分组，但 RSS 峰值仍达 544.16MiB，
未通过并保留。后续将每次 read/aggregate 的全数组 DOM 改为 Utf8JsonReader 逐行遍历，
仅为有界不同分组克隆标量键。384MiB 堆配置与 512MiB RSS 检查均保留，不改变进程验收上限。

d2ba61f 逐行/384MiB 实验答案仍正确，但峰值为 537.17MiB，原始失败继续保留。
下一轮明确将原 512MiB 进程预算划分为 320MiB managed heap 和 192MiB native/JIT/
宿主余量。两条路径使用相同配置，不强制 GC，也不据此宣称协议内存节省。

## 有界模型证据回放

`data-workflow-deepseek-runtime.py` 先要求完整实际 Release 矩阵通过，核对来源/引用、
C/D 完全相同文本、宿主出站策略和 RSS 门槛。随后才可按 A/B 相同 temperature、
非思考模式和输出上限，对每个规模/路径观察五次 DeepSeek 回复。运行时已算出分组和
异常谓词，两者回放相同工具证据；这个冻结机器 JSON 任务本身无需 LLM。这里测供应商
usage 和精确复述，不是模型主动规划的在线工具工作流，也不是 NCP 专属 token 节省。

脚本必须复用原 A/B 共享预算账本。扩展冻结运行时、来源、runner 和提示词 hash，
不修改原 cap、探针、提示词或费用。每次请求前预留，未知 usage 保留预留费用，已尝试/
不确定请求键永不自动重试，保留原 usage 和合成可见答案。重复键、非 JSON 数值及
浮点替代整数不计精确通过。不记录隐藏思考或凭据；原两次 alias 探针及后续请求都计入
用户的同一个 10 美元上限。
